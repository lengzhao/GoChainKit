# 路线图与待决事项

本页汇总已有交付和候选方向，不授权实现，也不代表已承诺时间表。

## 已交付的开发基线

格式无关 core/cap、可配置 Node、两类 PoW、账户/UTXO、静态签名 PoA、分支导入/同步、Bolt/内存、HTTP、密钥保存及 KV Journal；消费者与限制见 [status](status.md)。GOVM 首批基础能力完成，不代表完整 GOVM 链或 VM 已交付。

## 待确认的产品决策

- 主要用户与短期目标：应用链开发者、研究 SDK，还是生产基础设施？生产目标需要额外威胁模型、长期运行和性能验证。
- [原 DPoS 四组合目标](plans/2026-10-17-composable-consensus-ledger-design.md) 是否继续推进，和 GOVM、外部 VM 的先后顺序是什么？当前没有取消该目标的依据；静态 PoA 不算 DPoS 完成。
- 哪些 core/cap/HTTP/磁盘格式准备冻结兼容承诺？目前不能仅凭目录名“core”推断已发布稳定 API。
- GOVM 是参考协议族还是近期交付主线？不应将 GOVM 特有地址、gas、分片字段加入所有链的核心契约。

## 已有设计中的后续顺序

[GOVM 能力草案](plans/2026-10-20-govm-cap-design.md) 建议先贯通正文归档/补齐与消息 Router，再做专属单分片协议及 gas、合约框架、外部 VM，随后钱包/管理/观测；多分片和对象并行有独立前置设计。此顺序仅描述该方案，未替 DPoS 或生产目标做优先级决定。

`cap/contract` 当前 `CodeProvider.Code(ctx,id)` 和 `Runtime.Execute(ctx,request,host)` 仍是草案接口。上述设计拟把当前 Reader 和已验证 Artifact 显式传入；不能把拟议签名当作已实现 API，更不能先在外部 VM 冻结其兼容承诺。
