# 能力接口分层

`core` 是格式无关的基础契约；`cap/<能力>` 是可按实际需求演进的扩展契约；`model`、`protocol`、`runtime` 提供领域实现，`plugins` 使用类型化 Deps 装配。新增能力不进入基础 Block、Transaction 或 Protocol 的必选方法。

接口首先有明确消费者、替换需求与行为约束，再决定是否公开。每个插件完成一个内聚职责，通过 Deps 注入其他能力，不在内部隐藏构造子插件、不查询全局服务定位器。小接口按能力组合，不按每个方法机械拆插件。

## 依赖方向

- `cap` 只依赖 `core` 及必要的其他能力契约，不依赖领域实现、插件、PluginKit 或具体后端。
- 领域实现可以消费 `cap`；插件通过 Deps 提供实现，Config 仅保存可序列化配置。
- `cap` 根包不聚合全部接口。具体格式族的 Rule/Choice 继续留在 `protocol/composed`，它们依赖 Envelope，不适合反向搬进通用能力包。
- 既有分支、共识封印、网络、复制与资产扩展已归入对应 cap 子包；core 不反向依赖 cap。接口语义保持不变。

## 契约边界

执行上下文仍将历史限定在执行父块的确定性祖先链，禁止读当前主链回执索引及节点本地额外侧链。Candidate 是稳定执行视图，不把封印后的变化反灌为模型输入。

成员集合不强制权益和票重；签名服务不接管出块规则。 `PublicKey.Algorithm` 标识完整且版本化的签名套件，必须统一算法参数、公钥/签名编码、Domain 与载荷的规范编码及预哈希规则；同套件的独立 Signer／Verifier 实现必须互操作，不能自行选择 framing。不支持或不匹配的套件须在构造或校验时显式拒绝。首个实现套件为 `ed25519/gck-domain-v1`，编码见 [基础能力](govm-foundation.md)。引用体装配保持原 Block.ID 和规范线上编码，完整交易是附属数据；不同编码语义的格式不能谎称满足该契约。

Journal 的检查点仅属于单次执行、单个实例，Revert 和 Release 都按 LIFO 消栈。Release 只保留内存变更，不是持久提交；外层回滚仍能撤销内层成功调用。事件必须与调用状态一起回滚。成功/合约 Revert/OutOfGas 是确定性结果，本地取消或运行器故障返回 error；是否收费和消耗序号属于具体链规则。

Runtime 身份包含产物格式、指令语义和计费版本；代码内容寻址，不使用本地路径、时钟或超时决定链上执行结果。跨合约调用、资产转移和特定对象模型按需求增加可选能力，当前 Host 不强制这些字段。

## 装配与演进

必需能力通过非可选 Deps 在构造期验证，缺失或协议/创世绑定不兼容时启动失败。可选能力必须有明确降级语义：未配置合约 Runtime 就不接受合约交易，不能静默忽略；缺失 Materializer 就拒绝引用体区块，不能部分执行。

当前 cap 中尚无具体实现的新接口是可评审设计入口，不代表功能可用。后续用真实消费方验证后可以删减或调整；只有已有替换需要才进一步拆接口。不得通过添加空实现伪造支持。

基础查询 API、静态成员 PoA 与 Journal 已接入。后续可按实际需求推进引用体装配及缺失交易请求、事件与状态一体回滚 Host、独立确定性 Runtime；消息复用应在多个实际消息消费者接入时实现。动态成员、多分片证明与跨链执行仍是后续独立能力。
